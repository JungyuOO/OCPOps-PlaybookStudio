PBS Lightspeed 연동 운영 플로우 발표 설명서

이 문서는 PBS 챗봇이 OpenShift Lightspeed API와 PBS 내부 문서 RAG를 어떻게 함께 사용해 화면에 답변을 출력하는지, 발표 자리에서 쉽게 설명할 수 있도록 정리한 자료다.

작성일: 2026-06-08 Branch: feat/kugnus-dev2.3 HEAD: bdc7427 범위: Lightspeed 연동 / PBS RAG / Prompt / UI 출력

한 줄 결론

사용자가 이해한 “Lightspeed API에서 답을 가져오고, PBS 문서에서도 근거를 가져와서 화면에 조립해 보여준다”는 큰 방향은 맞다. 다만 현재 구현의 핵심은 Lightspeed가 성공하면 PBS가 답변 본문을 다시 생성하지 않고, Lightspeed 공식 답변을 우선 노출한 뒤 PBS 문서의 citation, 관련 문서, 뷰어 링크를 보조 근거로 붙이는 구조라는 점이다.

발표 표현으로는 “PBS가 공식 답변 생성기인 Lightspeed와 내부 운영 문서 라이브러리를 같이 조회해서, 공식 답변을 중심으로 관련 문서와 근거를 한 화면에 연결해 주는 운영형 RAG 게이트웨이”라고 설명하는 것이 안전하다.

맞는 인식과 보정할 인식

구분 설명 발표 시 표현
맞는 인식 PBS 챗봇은 OpenShift 운영 질문으로 판단되면 Lightspeed API를 호출한다. “OpenShift 운영성 질문은 Red Hat Lightspeed 쪽 공식 답변을 우선 확인합니다.”
맞는 인식 동시에 PBS 내부 문서 검색도 수행한다. Gold Playbook, 런타임 문서, 업로드 문서, 고객 데이터가 근거 후보가 된다. “PBS 내부 문서 라이브러리도 함께 검색해서 관련 근거와 문서 뷰어를 붙입니다.”
보정 필요 Lightspeed 성공 경로에서는 PBS LLM이 두 답변을 새로 합성해 본문을 다시 쓰는 방식이 아니다. “현재는 공식 답변을 훼손하지 않기 위해 Lightspeed 답변을 우선 보존하고, PBS 근거는 보조 연결합니다.”
보정 필요 고객 문서나 업로드 문서가 무조건 모든 운영 답변에 섞이는 것은 아니다. 질문 의도와 검색 결과에 따라 보조 citation으로 연결된다. “고객 문서 반영은 질문이 해당 문서 맥락을 요구할 때 더 강하게 동작하며, 범용 운영 질문에서는 공식 답변 우선입니다.”

현재 운영 플로우

1. 사용자 질문 입력 PBS 웹 화면에서 사용자가 운영 질문을 입력한다. 예: “Ingress 컨트롤러에 단일 NodePort 서비스 추가 내용을 초보자용 3단계로 정리해줘”
2. 질문 라우팅 질문이 OpenShift 운영 질문인지 판단한다. 운영 질문이면 Lightspeed 호출 후보가 된다.
3. Lightspeed API 호출 PBS backend가 Lightspeed /v1/query에 질문을 보낸다. 응답은 공식 답변 artifact로 저장된다.
4. PBS 내부 RAG 검색 PBS가 내부 Gold/runtime 문서, 사용자 업로드, 고객 데이터 등에서 관련 근거를 검색하고 citation context를 조립한다.
5. 답변 경계 결정 Lightspeed 성공이면 answer_source=lightspeed_with_pbs_rag, 실패 또는 미대상이면 pbs_rag가 된다.
6. 화면 payload 생성 답변 본문, citation, related links, related sections, primary badge를 하나의 chat payload로 만든다.
7. UI 출력 화면에는 Lightspeed/GOLD PLAYBOOK/User Upload/Customer Data 같은 badge와 함께 답변, 관련 문서, 바로 볼 절차가 표시된다.
8. 문서 뷰어 연결 citation 또는 관련 문서를 클릭하면 PBS viewer가 해당 Gold/runtime/upload/customer 문서나 Lightspeed artifact를 연다.

성공/실패 경로별 동작

상황 답변 본문 근거/출처 표시 의미
Lightspeed 성공 + PBS citation 있음 Lightspeed 공식 답변을 그대로 우선 사용 Lightspeed 외부 답변 citation이 1번으로 붙고, PBS citation은 뒤로 밀려 표시 현재 가장 정상적인 연동 경로
Lightspeed 성공 + PBS citation 없음 Lightspeed 공식 답변을 그대로 사용 PBS citation 없이 Lightspeed artifact만 근거로 남음 공식 답변은 왔지만 내부 문서 연결은 부족한 상태
Lightspeed 실패, timeout, 미설정 PBS 내부 RAG와 내부 LLM prompt로 답변 생성 Gold/runtime/upload/customer 문서 citation 표시 Lightspeed 없는 상황에서도 PBS 자체 지식으로 답변
근거 부족 무리해서 답변하지 않고 clarification/no-answer 성격으로 응답 가짜 citation을 만들지 않음 시스템 신뢰성을 지키기 위한 방어 동작

Lightspeed API로 보내는 내용

Lightspeed API 호출은 PBS 내부 문서 전체를 붙인 긴 RAG prompt가 아니다. 기본 구조는 사용자의 질문을 정규화한 뒤 Lightspeed /v1/query로 전달하는 방식이다. 필요하면 설정값에 따라 provider, model, system prompt도 같이 보낼 수 있다. 

{
  "query": "사용자 질문을 정규화한 문자열",
  "conversation_id": "선택 값",
  "provider": "환경변수로 지정된 경우",
  "model": "환경변수로 지정된 경우",
  "system_prompt": "환경변수 OPENSHIFT_LIGHTSPEED_SYSTEM_PROMPT가 있는 경우"
}
  • OPENSHIFT_LIGHTSPEED_BASE_URL이 있으면 /v1/query endpoint로 호출한다.
  • OPENSHIFT_LIGHTSPEED_TIMEOUT_SECONDS는 현재 기본값 60초다.
  • OPENSHIFT_LIGHTSPEED_INSECURE_SKIP_TLS_VERIFY 설정에 따라 TLS 검증 여부가 결정된다.
  • 한국어 오타 중 잇을 있으로 보정하는 정규화가 적용된다.
발표용 표현: “PBS가 Lightspeed에게는 질문 자체를 공식 답변 요청으로 보냅니다. Lightspeed 내부에서 자기 RAG를 수행하고, PBS는 받은 답변과 참조 정보를 artifact로 저장한 뒤 화면에 연결합니다.”

PBS 내부 LLM 프롬프트

PBS 내부 LLM 프롬프트는 src/play_book_studio/answering/prompt.py에서 만들어진다. 이 프롬프트는 PBS 내부 RAG 답변을 생성할 때 사용하며, 주요 규칙은 다음과 같다.

  • 제공된 문서 근거만 사용한다.
  • 답변은 한국어로 친절하지만 군더더기 없이 작성한다.
  • 근거 번호는 [1], [2]처럼 citation으로 단다.
  • 근거에 없는 명령어, 옵션, 버전, 수치, 원인, 설정값을 추측하지 않는다.
  • OpenShift Lightspeed 공식 답변 블록이 제공되면 그 내용을 우선하고, 명령어와 URL을 바꾸지 않는다.
  • PBS 근거는 고객사 기준이나 내부 문서 맥락을 보충할 때만 사용한다.
system:
  당신은 OpenShift(OCP) 운영을 돕는 기술 가이드입니다.
  제공된 문서 근거만 사용해 한국어로 답하세요.

user:
  질문: {사용자 질문}

  세션 맥락: {있으면 포함}

  OpenShift Lightspeed 공식 답변:
  {있으면 포함}

  근거:
  {PBS 내부 RAG citation context}

  지시:
  Lightspeed 공식 답변이 있으면 우선 유지하고,
  PBS 근거는 보충 맥락으로만 사용하세요.
중요한 차이: 현재 일반적인 Lightspeed 성공 경로에서는 PBS LLM이 이 프롬프트로 답변 본문을 다시 생성하기 전에 Lightspeed 원문 답변을 passthrough로 반환한다. 따라서 이 프롬프트는 내부 RAG 답변 경로 또는 향후 합성 경로의 규칙으로 이해하는 것이 정확하다.

화면 출력 구조

API 응답 payload에는 답변 본문만 있는 것이 아니라, 출처와 뷰어 연결을 위한 메타데이터가 같이 포함된다.

필드/개념 역할
answer 사용자에게 보이는 답변 본문. Lightspeed 성공 시 Lightspeed 답변이 우선 들어간다.
answer_source lightspeed_with_pbs_rag 또는 pbs_rag처럼 답변 경계를 표시한다.
citations 답변에 표시되는 [1], [2] 출처 목록. Lightspeed 성공 시 외부 Lightspeed citation이 앞에 붙는다.
related_links 관련 문서 카드. Gold Playbook, User Upload, Customer Data, Lightspeed artifact viewer로 연결된다.
related_sections 바로 볼 절차 또는 문서 내 섹션 연결.
primary_boundary_badge UI badge. 예: Lightspeed, Lightspeed + Customer, GOLD PLAYBOOK.

어른들께 설명하는 30초 버전

“PBS 챗봇은 OpenShift 운영 질문이 들어오면 먼저 Red Hat OpenShift Lightspeed에 공식 답변을 요청합니다. 동시에 PBS가 보유한 Gold Playbook, 런타임 문서, 사용자 업로드, 고객 데이터도 검색해서 관련 근거와 문서 링크를 찾습니다. Lightspeed가 정상 응답하면 공식 답변을 그대로 우선 보여주고, PBS 문서들은 참고 근거와 뷰어 링크로 붙입니다. Lightspeed가 실패하거나 대상 질문이 아니면 PBS 내부 RAG와 LLM prompt로 근거 기반 답변을 생성합니다. 그래서 PBS는 단순 챗봇이라기보다 공식 지식과 현장 문서를 한 화면에서 연결하는 운영 지원 게이트웨이입니다.”

발표 때 피해야 할 표현

  • 피함: “PBS가 Lightspeed 답변과 모든 고객 문서를 항상 자동 합성합니다.”
  • 권장: “현재는 공식 답변 보존을 우선하고, PBS 문서는 citation과 뷰어 링크로 보조 연결합니다.”
  • 피함: “고객 PPT가 들어오면 무조건 고객 맞춤 답변이 완성됩니다.”
  • 권장: “고객 데이터는 질문이 해당 맥락을 요구할 때 반영되며, 문서 품질과 파싱 품질이 답변 품질에 영향을 줍니다.”
  • 피함: “PBS가 Lightspeed 내부 RAG를 직접 수정합니다.”
  • 권장: “Lightspeed는 외부 공식 답변 provider이고, PBS는 그 결과를 호출·저장·표시·보조근거 연결하는 쪽입니다.”

현재 한계와 다음 과제

항목 현재 상태 다음 과제
Lightspeed 응답 지연 질문에 따라 35초를 넘길 수 있어 timeout을 60초로 여유 조정했다. 시연 질문셋은 사전 smoke로 응답 시간을 확인하고, 장기적으로 비동기/streaming UX를 검토한다.
고객 데이터 결합 고객 데이터 citation 연결은 가능하지만 PPT/이미지 기반 문서는 파싱 품질이 들쑥날쑥하다. 운영 질문에 쓰려면 고객 문서를 운영 체크리스트/절차형 corpus로 정제하는 전처리 단계가 필요하다.
업로드 문서와 공식 답변의 합성 active upload 기준 답변은 가능하지만, Lightspeed+upload를 항상 자연스럽게 합성하는 경로는 아직 제한적이다. “공식 답변 + 고객/업로드 문서 보충”을 별도 answer mode로 설계하고 평가 질문셋을 만든다.
출처 신뢰성 Lightspeed artifact, Gold/runtime viewer, upload/customer viewer를 구분해 badge와 source lane을 표시한다. 시연 전에 citation 클릭이 실제 해당 viewer로 가는지 반복 확인한다.
