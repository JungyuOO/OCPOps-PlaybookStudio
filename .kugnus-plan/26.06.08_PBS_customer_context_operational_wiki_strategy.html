PBS 고객 맞춤 운영 위키 답변 전략

PBS의 목표는 Lightspeed 답변을 단순 중계하는 챗봇이 아니라, 고객 환경의 사실과 OpenShift 운영 지식을 결합해 현장 운영 판단을 돕는 위키형 운영 도구가 되는 것이다.

1. 핵심 판단

고객이 올린 문서, PPT, PDF는 고객 환경에서 사실로 취급해야 한다. 따라서 고객문서 자체가 답인 질문에서는 Lightspeed가 주도권을 가지면 안 된다. Lightspeed는 OpenShift 제품 동작, 공식 운영 기준, 점검 명령, 장애 분석 원리를 보강할 때 사용한다.

고객문서가 주도하는 경우 CI 순서, 내부 절차, 사내 URL, 교육자료, 고객 환경 네이밍, 고객이 정한 운영 규칙을 묻는 질문.
Lightspeed가 주도하는 경우 OpenShift 리소스 상태, Operator 장애, Pod/PVC/PipelineRun 장애, 공식 점검 명령을 묻는 운영 질문.
결합이 필요한 경우 고객문서의 절차나 제약이 장애 분석의 전제가 되고, OpenShift 공식 운영 지식으로 점검 순서를 보강해야 하는 질문.

2. 지식 우선순위

우선순위 지식 원천 역할 답변에서의 표현
1 고객 업로드/PPT/PDF 고객 환경의 사실, 내부 절차, 현장 기준 User Upload, Customer Context
2 현재 콘솔/클러스터 상태 실제 리소스 상태, 이벤트, 설치/장애 진행 상황 Console Runtime, Cluster State
3 OpenShift Lightspeed 공식 운영 설명, 점검 순서, 제품 동작 기준 Lightspeed
4 Gold Playbook PBS 내부 검증 runbook, fallback 운영 근거 Gold Playbook

3. 실제 고객 시나리오

시나리오 A: 고객문서 자체가 답인 질문

질문: CI 순서 핵심 알려줘

이 질문은 고객이 업로드한 CI 순서 문서가 정답이다. OpenShift 일반 지식보다 고객이 정리한 절차가 우선한다. 

답변 출처: User Upload

고객 업로드 문서 기준 CI 순서는 다음 흐름입니다.
1. Git 저장소를 Pipeline에 연결
2. GitHub Webhook 설정
3. smee URL과 Webhook secret 설정
4. .tekton/push.yaml 구성
5. Git push 후 PipelineRun 실행 확인

근거: CI 순서 업로드 문서 [1]

시나리오 B: 고객문서가 운영 판단의 전제가 되는 질문

질문: 우리 CI에서 push해도 PipelineRun이 안 떠. 어디부터 봐야 해?

이 질문은 고객문서와 Lightspeed 결합이 필요하다. 고객문서는 이 환경의 CI 구성 방식을 알려주고, Lightspeed는 OpenShift/Pipelines 기준 점검 순서를 보강한다. 

답변 출처: Lightspeed + Customer Context

고객 문서 기준으로 이 환경의 CI 흐름은
Git 저장소 연결 -> Webhook 설정 -> smee URL 사용 -> secret 설정 -> .tekton/push.yaml 구성입니다. [고객문서 1]

따라서 이 환경에서는 먼저 다음을 확인합니다.
1. GitHub Webhook Payload URL이 고객 문서의 smee URL 흐름과 맞는지 확인
2. Webhook secret이 OpenShift 쪽 secret과 일치하는지 확인
3. Repository 또는 PipelineRun 생성 이벤트 확인
4. Pipeline controller 로그와 이벤트 확인

OpenShift 기준으로는 Webhook 수신, Repository CR, PipelineRun/Event 순서로 좁히는 것이 적절합니다. [Lightspeed 1]

시나리오 C: 공식 운영 지식이 우선인 질문

질문: CSV가 정상 전환되지 않을 때 Subscription, InstallPlan, CSV를 어떤 순서로 확인해?

고객문서에 특정 Operator 설치 절차가 없으면 Lightspeed가 주도한다. 고객문서에 사내 설치 절차나 namespace, operator name이 있으면 그 부분만 맥락으로 결합한다.

4. 바람직한 답변 형식

답변은 단순히 출처를 나열하는 것이 아니라, 각 출처의 역할을 분리해서 보여줘야 한다. 특히 고객문서와 Lightspeed가 함께 쓰인 경우에는 상단 라벨이 Lightspeed 단독이면 부족하다.

질문 유형 주도 출처 보조 출처 상단 라벨
고객 절차 요약 고객문서 없음 User Upload
고객 절차 기반 장애 분석 Lightspeed 또는 콘솔 상태 고객문서 Lightspeed + Customer
OpenShift 일반 운영 질문 Lightspeed Gold Playbook Lightspeed
내부 runbook 기반 조치 Gold Playbook Lightspeed 실패 시 없음 Gold Playbook

5. 현재 1차 연동 작업 방향

  1. User Upload citation 라벨 정리: 업로드 문서 citation이 Gold나 Source-First처럼 보이지 않도록 User Upload로 직렬화한다.
  2. 결합 답변 primary badge 추가: Lightspeed 답변에 고객문서 citation이 붙으면 Lightspeed + Customer로 표시한다.
  3. Trace 증거 보존: external_answer.context_bridge.customer_context_applied=true를 남겨 재현 로그에서 결합 이유를 확인할 수 있게 한다.
  4. 본문 합성은 다음 단계: Lightspeed 원문을 임의로 재작성하지 않고, 먼저 출처 계약과 UI 신호를 안정화한다.

6. Acceptance Criteria

항목 Pass 조건 검증 방법 현재 Gap
고객문서 단독 답변 CI 순서 요약 질문에서 고객 업로드 문서가 primary로 표시된다. /api/chat payload의 citation/source badge 확인 질문 의도별 라우팅 정교화 필요
Lightspeed + 고객문서 결합 Lightspeed 성공 답변에 업로드 citation이 붙으면 primary badge가 Lightspeed + Customer가 된다. unit test 및 chat payload 확인 1차 연동 대상으로 반영
출처 뷰어 고객 업로드 문서는 viewer에서 원본 이미지와 본문이 확인 가능하다. 업로드 문서 viewer HTML 확인 이미지 표기 개선 반영 완료
본문 합성 고객문서 전제와 Lightspeed 점검 순서가 한 답변 안에서 역할 분리되어 서술된다. 실제 운영 질문 smoke test 다음 단계에서 합성 프롬프트/정책 필요

7. 결론

PBS의 이상적인 형태는 Lightspeed를 항상 앞세우는 구조가 아니다. 고객문서가 사실인 영역은 고객문서가 답하고, 운영 판단에는 Lightspeed와 콘솔 상태가 보강되어야 한다. 이번 1차 연동은 이 제품 방향을 UI와 trace 계약으로 고정하는 작업이다.
