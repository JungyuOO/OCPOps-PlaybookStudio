PBS Lightspeed 시연 안정화 작업목표

OpenShift 운영 질문에서 Lightspeed를 우선 호출하고, PBS 내부 RAG는 정확한 출처와 뷰어를 보강하는 시연 안정화 목표 문서.

1. 목표

이번 작업의 목표는 PBS를 고객맞춤 운영도구 완성본으로 과장하는 것이 아니라, OpenShift 운영 질문에서 Lightspeed 연동이 안정적으로 동작한다는 것을 시연 가능한 상태로 고정하는 것이다.

운영 질문이 들어오면 PBS는 OpenShift Lightspeed를 공식 답변 엔진으로 우선 호출한다. Lightspeed 응답이 성공하면 답변 본문은 Lightspeed 원문을 기준으로 보여주고, PBS 내부 RAG는 Gold Playbook, User Upload, Customer 문서 같은 보조 근거와 뷰어 링크를 붙이는 역할을 한다.

2. 완료 조건

라우팅

OpenShift, Operator, Pipeline, PAC, Tekton, Ingress, NodePort, oc, kubectl 류 운영 질문은 Lightspeed 호출 대상이다.

멀티턴

이전 문맥이 OpenShift 운영 주제이고 현재 질문이 실패 지점, 확인, 주의사항, 절차를 묻는 경우에만 후속 질문도 Lightspeed로 보낸다.

출처

Lightspeed 성공 시 [1]은 항상 /external/lightspeed/{artifact_id} 뷰어로 연결된다.

Fallback

미설정, timeout, error, empty 응답은 pipeline_trace.external_answer.status에 남긴다.

3. 현재 운영 플로우

  1. 사용자가 PBS 챗봇에 질문을 입력한다.
  2. PBS가 질문과 세션 문맥을 보고 Lightspeed 호출 대상인지 판정한다.
  3. 대상이면 PBS가 OpenShift Lightspeed API에 POST /v1/query를 호출한다.
  4. Lightspeed가 내부 RAG와 모델을 통해 답변을 생성해 반환한다.
  5. PBS는 별도로 내부 RAG를 실행하여 Gold, User Upload, Customer 문서 근거를 찾는다.
  6. Lightspeed 응답이 성공하면 답변 본문은 Lightspeed 기준으로 표시하고, 내부 RAG 근거는 관련 문서와 citation으로 결합한다.
  7. Lightspeed가 실패하거나 응답이 비어 있으면 PBS 내부 RAG 답변으로 fallback한다.

4. Lightspeed API 요청과 응답 계약

구분 내용
Endpoint POST /v1/query
필수 body query
Optional body conversation_id, provider, model, system_prompt
Header Content-Type: application/json, token 설정 시 Authorization: Bearer {token}
Timeout OPENSHIFT_LIGHTSPEED_TIMEOUT_SECONDS, 현재 기본 60초
TLS OPENSHIFT_LIGHTSPEED_INSECURE_SKIP_TLS_VERIFY 설정에 따라 검증 여부 결정

PBS가 Lightspeed에서 받아 보존하는 값은 response/answer, conversation_id, referenced_documents, truncated, token metadata, tool metadata, raw payload이다.

중요한 경계

PBS는 Gold/User Upload/Customer 문서를 Lightspeed 요청 body에 직접 주입하지 않는다. Lightspeed는 자기 내부 RAG로 답변을 만든다. PBS 내부 RAG는 그 뒤에 별도로 실행되어 출처, 관련 문서, 뷰어 연결을 보강한다.

5. Fallback 정책

Status 의미 UI/보고 기준
not_applicable Lightspeed 대상 질문이 아님 PBS 내부 RAG 기준
disabled Lightspeed base URL 미설정 내부 RAG fallback, 미설정 trace 보존
error API 오류 또는 timeout 내부 RAG fallback, 오류 trace 보존
empty API 응답은 왔지만 답변 본문이 비어 있음 내부 RAG fallback, 빈 응답 trace 보존
used Lightspeed 답변을 실제 사용함 Lightspeed citation과 viewer를 최우선 표시

시연에서 중요한 점은 항상 Lightspeed처럼 보이기가 아니다. 중요한 것은 Lightspeed를 써야 하는 질문에서는 우선 호출하고, 실패하면 실패 상태가 추적 가능하며, PBS 내부 RAG 답변과 외부 Lightspeed 답변의 경계가 UI와 로그에서 섞이지 않는 것이다.

6. 고객문서와 업로드 문서 판단

고객문서와 업로드 문서는 고객 맞춤 운영도구로 가기 위한 중요한 데이터지만, 이번 안정화 범위에서는 품질이 충분한 검색 hit가 있을 때만 답변 근거로 붙인다.

  • 사용자의 질문과 실제 chunk 본문이 의미 있게 연결된다.
  • viewer에서 사용자가 해당 근거를 확인할 수 있다.
  • 출처 라벨이 User Upload, Customer Data, Gold Playbook, Lightspeed 중 무엇인지 명확하다.
  • 고객 데이터가 없을 때도 Lightspeed 공식 답변 흐름은 독립적으로 동작한다.

Runtime smoke

  • Ingress 컨트롤러에 단일 NodePort 서비스 추가 내용을 초보자용 3단계로 다시 정리해줘: 60초 timeout 내 성공 시 Lightspeed 우선 응답
  • 내 Git 저장소 이름을 바꾸는 방법 알려줘: OpenShift 운영 질문이 아니므로 Lightspeed 미호출
  • User Upload 기반 CI 문서 질문 뒤 흔한 실패지점은 뭐야?: 문맥상 OpenShift/Pipeline 후속 질문이면 Lightspeed 호출, 업로드 citation 보존

8. 하지 않을 것

  • 고객 PPT를 무조건 답변에 끼워 넣지 않는다.
  • Lightspeed 내부 RAG가 어떤 문서를 선택했는지 PBS가 통제한다고 말하지 않는다.
  • Fallback 결과를 Lightspeed 답변처럼 보이게 만들지 않는다.
  • 기존 .kugnus-plan 삭제/rename 상태는 이번 작업 목표와 섞지 않는다.

9. 보고용 한 줄 설명

PBS 2.3의 시연 안정화 목표는 OpenShift 운영 질문에 대해 Lightspeed를 공식 답변 엔진으로 우선 호출하고, PBS 내부 RAG는 Gold/업로드/고객문서 근거와 뷰어를 정확히 붙여 출처가 섞이지 않는 운영 챗봇 흐름을 만드는 것이다.
